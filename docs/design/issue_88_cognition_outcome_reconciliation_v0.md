# Issue #88 — Provider-neutral cognition outcome reconciliation, design v0

**Status:** proposed design; implementation **not authorized** by this record  
**Date:** 2026-10-08  
**Base:** Gen2 Core on `main`; separate from the closed DW3 pilot  
**Tracking:** [Issue #88](https://github.com/kymuco/codexia-manual-agent/issues/88)

## 1. Problem and boundary

A `CognitionHandoff` is durably recorded before `CognitionPort.complete()` is called. The external provider may complete a response while the process fails before `CognitionOutcome` is admitted. The persisted `RoleRun` stays `REQUESTED` with an existing handoff. Current bounded progression correctly returns quiescent and does **not** dispatch again.

DW3 exercised one manual recovery path: an already completed ChatGPT response was read through CWA, reconciled with the durable handoff and exact prompt, then admitted via `CognitionTransportBridge.record_outcome()`. Its Research Work stayed active because the synthesis stated `material_uncertainty_resolved=false`. DW3 is evidence for **one** recovery case, not a general provider guarantee.

**Goal:** define how a host can inspect and conditionally admit a **previously executed** cognition result, without acquiring a new dispatch/retry authority or modifying domain-specific completion criteria.

**Strict non-goal:** re-arming a provably unsubmitted effect (issues [#21](https://github.com/kymuco/codexia-manual-agent/issues/21) and [#23](https://github.com/kymuco/codexia-manual-agent/issues/23)). Human admission of a *returned result* is distinct from human permission to *retry a dispatch*.

## 2. Existing contracts (verified in main)

- `role_core/transport_bridge.py`: `dispatch_once` records the handoff before calling the port; presence of an existing handoff suppresses redispatch; `record_outcome` validates Work/Workflow/Role/request/port bindings, rebinds the outcome to the current Work snapshot and delegates to `RoleAdmission`.
- `role_core/transport_models.py`: `CognitionHandoff` contains `handoff_id`, `port_id`, request/role/Work/Workflow identities and digests, and the event frontier. It **does not** prove attempted dispatch or provider completion.
- `role_core/transport_projection.py`: at most one handoff per request; event/prefix/binding checks.
- `workflow_orchestration/existing_work_progression.py`: a requested RoleRun with an admitted handoff returns `False` and yields quiescence, not a fresh port call.
- `providers/model_provider_cognition.py`: the generic provider adapter returns an output as `CognitionOutcome.succeeded` but does not persist provider turn IDs, response evidence, or request-to-provider correlation. The existing ordinary `record_outcome()` path does not claim a provider-result identity in an installation-wide index. Therefore current and historical live admissions must be considered **unindexed**, not automatically safe to reconcile.
- `role_core/admission.py`: `admit_outcome` has an idempotent replay path **for the same outcome event identity**, not necessarily for independently minted outcome IDs or conflicting results.
- `role_core/models.py`: `CognitionOutcome` supports succeeded/failed/unknown and contains the returned text digest. `UNKNOWN` is a terminal role outcome and is **not** an appropriate default merely because historical provider observation is missing.

Therefore: retain Gen2's existing handoff/role/admission logic, add reconciliation as a **host-orchestrated, explicitly authorized observation and proof flow**. No new model message may be generated by reconciliation.

## 3. Two separate dimensions of truth

Do not flatten the lifecycle and evidence into one ambiguous enum:

| Fact | Source of truth | Implication |
| --- | --- | --- |
| Cognition request admitted | Work events | Exact semantic input/binding exists |
| Handoff admitted | Work events | Exactly one request routed to a port |
| Dispatch attempt started | Trusted transport observation, when available | Not a receipt |
| Provider accepted write | Provider receipt/correlation, when available | Effect may have occurred |
| Provider completed response | Provider read/receipt | External result may be available |
| Response observed read-only | Reconciliation provider observation | Candidate bytes and metadata |
| Outcome admitted | Work `role.completed` / `role.failed` | Durable RoleRun result |
| Completion claim accepted | Domain workflow criterion | Work-level completion; independent |

A request may have `handoff_admitted=true` and every provider-execution facet **unknown**. Absence of a provider result is not proof of `NOT_SUBMITTED`. Never infer success merely from a response-shaped text blob.

## 4. Proposed architecture

```text
  Durable WorkStore                Host-only read path             Provider read
  Request + Handoff ───────────────→ RecoveryScope ───────────────→ Observation
  Requested RoleRun                   │                                 │
                                     └─────────→ Pure verifier ←────────┘
                                                    │
                                       UNVERIFIABLE / CONFLICT
                                                    └──→ No Work writes
                                                    │
                                      Corroborated candidate
                                                    ↓
                                    Authenticated policy/human gate
                                                    ↓
                         Storage-enforced writer epoch barrier (legacy fence)
                                                    ↓
                           Host-wide coverage gate (live + recovered outcomes)
                                                    ↓
                              Host-wide ProviderResultClaimIndex (atomic unique)
                                                    ↓
                                 Frontier-bound Work proof attempt (CAS)
                                                    ↓
                           NEW strict expected-head CognitionOutcome admission
                                 (WorkStore final append CAS; NOT current
                                    record_outcome() snapshot rebinding)
                                                    ↓
                                      Re-project durable RoleRun
```

**Proposed interfaces** (names illustrative; not committed public APIs):

- `RecoveryScope`: immutable {`work_id`, `workflow_run_id`, `role_run_id`, `request_id`, `request_digest`, `handoff_id`, `handoff_digest`, `port_id`, `expected_work_revision`, `expected_head_digest`, `provider_capability_id/version`}. Constructed from validated Work chronology, not caller-provided untrusted assertions.
- `ProviderReadPort.inspect(scope, locator) -> Observation`: *read-only* existing response/receipts. Provider-specific implementation retains credentials and conversation handles; may return `UNSUPPORTED` / `NOT_FOUND` / `AMBIGUOUS` / observed data. No `send`, `retry`, `create_conversation`, or other effectful fallback.
- `Observation`: request/response identity and parent or branch lineage (if exposed), provider completion signal, raw response bytes/hash, captured request/wire prompt digest or provider-side correlation token, read source and capability version, transformation metadata, and trust/provenance. An observation is **evidence**, not a `CognitionOutcome` or dispatch authorization.
- `ReconciliationVerifier`: pure, bounded comparison between durable scope and provider observation(s). Returns a closed `ProofDecision`, never invokes a provider or changes Work.
- `AdmissionGate`: separately confirms exact current durable frontier, caller authorization, proof policy, canonical output and existing handoff. It must invoke a **new expected-head CAS outcome admission boundary** that checks the authorized revision/digest on the final WorkStore append. The existing `record_outcome()` rereads and rebinds to the latest snapshot, so an earlier preflight plus that method is insufficient. It does not call the provider.
- `ProviderResultClaimIndex`: an atomic durable claim over stable provider service identity + authenticated tenant/account namespace + immutable provider-side execution/turn (or conversation namespace) + response ID **across all Work IDs within the installation**. Adapter version and serializer version are metadata, **never part of the uniqueness key**. On adapter upgrades, aliases/migrations must preserve one claim for one external result. The **same** global index must be populated by normal **live callback admission** and reconciliation; a recovered response must never be claimed after ordinary admission into another Work. If stable identity, cross-version mapping, index read, index write, or **historical coverage** is unavailable, reject reconciliation admission even with human contextual approval. The claim grants no dispatch or completion authority.
- `ProviderResultCoverageGate`: host-maintained, durable proof that live and recovered admission paths share claim-index coverage for this provider/account namespace and its relevant historical result window. Existing legacy `record_outcome()` does **not** write such claims. Do not enable reconciliation merely because the index was freshly initialized or an adapter was upgraded; require verified backfill or a provider-supported exclusion fence for pre-index results **AND a storage-enforced writer-epoch activation barrier** that prevents previously-running old callbacks from appending after cutover. Without both proofs, the namespace stays disabled for reconciliation.
- `LegacyWriterFence`: a database-serialized, mandatory write-epoch/format boundary that rejects outcome appends from legacy processes which do not use the claim index. A callback already executing before cutover must be forced to commit before the barrier or be rejected by storage if it attempts to append later. A process-local guard, shutdown assumption or timestamp is insufficient. Newly admitted live and recovered outcomes must both validate current epoch + result claim in the same final-append transaction; unsupported storage backends must fail closed.

Avoid giving `CognitionPort` generic WorkStore, credentials, workspace authority or introspection powers. The read port belongs at the **host/provider integration boundary**, not in `RoleCore`. Research Pack-specific trailer parsing remains an application-level canonicalization policy, never a Gen2 generic grammar.

## 5. Verification and trust policy

**Binding checks (mandatory):**

1. Recover exactly one active Work and requested RoleRun; validate Work/Workflow/Role/request digests, exact port routing and one admitted handoff. Recover the original `CognitionRequest` from its durable record and content digests, not a reconstructed *new* request.
2. Validate the caller's expected Work head, bind the proof-attempt to it, and enforce the **exact authorized post-proof head** atomically at the final outcome append via WorkStore CAS (revision **and** prior event digest). Do not use the current bridge's snapshot rebinding as a CAS gate. If the frontier moved, fail; a later retry requires a **new proof-attempt identity** for the new frontier, not reuse of an event ID with changed content.
3. Verify provider-side response is complete, the request precedes it, and the response is uniquely selected from the **correct** branch/execution. Check intervening prompts, sibling branches, edits, and alternate completions.
4. Bind the exact original wire input. A digest of semantic `CognitionRequest` is **not always** a digest of the provider prompt: adapters may prepend system instructions or replace context with a hot-conversation delta. A versioned wire-serialization/projection policy and observed provider input are needed. When exact bytes are not reconstructable, say so.
5. Check the full raw response bytes/hash, canonicalization version, canonical bytes/hash, and bounded output size. Never change control/judgment booleans or silently drop non-wrapper content. Preserve both digests and the transformation description.
6. Establish trusted provider identity and authenticated read provenance, including tenant/account namespace where applicable. No credentials, access tokens or raw private session state in generic Work events.

**Proof levels (proposal):**

- `EXACT_PROVIDER_CORRELATED`: a provider receipt or immutable turn/execution identifier explicitly bound to the original request/attempt, an authenticated completed response, and exact content provenance. May be eligible for configured, policy-approved admission; **never** confers permission to redispatch.
- `CONTEXT_CORROBORATED`: a unique read-only response matches the exact prompt/branch/history, but no trusted original request-to-provider receipt exists. May be presented for human-authorized result admission with a durable statement of residual ambiguity; must not be auto-admitted as cryptographically exact.
- `UNVERIFIABLE`: only text similarity, approximate timestamps, guessed conversation IDs, incomplete capture, unavailable branch history or missing provider provenance. Read-only report only.
- `CONFLICT`: mismatched digest/identity, multiple plausible responses, changed content or inconsistent provider proof. No admission, even with a generic "approve" click; requires separate adjudication and preserved evidence.

Human authorization **does not manufacture provider proof**, lift a conflict to `EXACT_PROVIDER_CORRELATED`, or authorize a retry. If the project's policy permits a human-assisted `CONTEXT_CORROBORATED` admission, persist its **distinct** human attestation and the proof level; the resulting RoleRun outcome remains visibly qualified in audit/provenance.

## 6. Failure and concurrency semantics

- **Crash before handoff:** no handoff: this protocol has nothing to reconcile; normal progression is separately governed.
- **Crash after handoff, before provider call:** provider submission unknown; remain `REQUESTED`; no inferred retry.
- **Crash after provider accepted write, before response:** an authenticated pending state is not a result; record/return observation if policy allows, but no completed outcome.
- **Crash after external completion, before local response capture:** read-only provider history may identify and recover result if sufficient proof exists; otherwise remain unresolved.
- **Crash after response capture/proof, before outcome admission:** persist/provide immutable, **frontier-bound proof-attempt** and provider-result claim; admission can resume only if the authorized post-proof frontier still matches. If Work has advanced, create a new proof attempt after read-only verification. The source result remains assigned to its original handoff. If proof cannot be validated, fail closed.
- **Crash after outcome append, before acknowledgement:** locate the already admitted role outcome; repeat reports `ALREADY_ADMITTED` when identity/digest match, with **zero new events**. Different response/result IDs or mismatched digest yield conflict, not a second terminal event.
- **Concurrent observers and live callbacks:** multiple read-only probes allowed; the same host-wide atomic provider-result claim covers **both** live callback and reconciled results, rejects cross-Work reuse, and at most one matched role outcome may append through strict expected-head CAS. The loser re-projects, compares and either reports ALREADY_ADMITTED or CONFLICT. A legacy unindexed callback makes reconciliation coverage unproven and disables admission for that namespace. A legacy callback racing activation is serialized before the epoch barrier (included in backfill) or rejected by storage after it: never allowed to append an unindexed result after activation.
- **Unavailable provider:** report `READ_UNAVAILABLE`/`UNSUPPORTED`; do not convert the RoleRun to terminal `UNKNOWN` solely from a transport timeout or absence of history.
- **Observation after Work cancellation/terminalization:** no admission; no resurrection of role or Work.
- **Observed incomplete/edited/branched response:** no completion; never choose "latest" if identity/lineage is ambiguous.

## 7. Durability and idempotency decisions to resolve before implementation

Do **not** assume `CognitionTransportBridge.record_outcome` is sufficient as an audit event on its own. Its current outcome record has no provider receipt ID or reconciliation proof envelope.

The proposed design prefers a small, versioned, immutable `ReconciliationProof` with:

- linkage to original request and handoff digests;
- provider ID/namespace, capability version, execution/turn + request-message and response-message IDs when available;
- raw/canonical response digests, canonicalization policy version and completion signal;
- proof level, conflicts/ambiguity flags and read provenance; human decision reference if used;
- expected Work frontier and a deterministic proof identity (not a timestamp-derived random key).

Require both a **storage-enforced epoch barrier** and durable namespace **coverage proof** first: both normal live callbacks and recovery must acquire the same host-wide provider-result claim keyed by provider-side identity across adapter versions. A legacy writer already in flight before migration must be serialized before barrier activation or fail at storage append after it. Today the normal `record_outcome()` callback does not claim results or enforce a writer epoch, and historical unindexed outcomes may exist, so neither protection is **currently established**. After verifying a complete historical backfill or provider-supported exclusion fence, acquire the **host-wide result claim** (atomic unique index), then a **frontier-specific Work proof event**, then admit through an explicit **strict expected-head CAS API**. Refuse reconciliation admission if coverage cannot be proved, or the index cannot reliably read/write, or stable result identity is missing; no per-Work or human-approval fallback. A proof event alone must never imply completion. If Work advances after the proof event, append a **new proof attempt at the new frontier with a new proof-event ID** after renewed read-only verification; do not reuse its old event identity with different bytes. Keep claim identity stable across these retries. The existing `CognitionTransportBridge.record_outcome()` is **not** the required strict CAS API because it silently binds to the newest Work snapshot. Re-project after each write, fail closed on missing claim-index guarantees, and never persist auth/session tokens. The exact transaction schema remains future work.

**Proposed resolution:** [ADR-001 — proof authority, receipts, human approval and replay](issue_88_adr_001_reconciliation_proof_authority.md) selects a Work-chronology proof association, causal provider receipts for the exact tier, explicitly authorized context-only recovery, and deterministic replay identity. These choices are **not yet implemented or externally reviewed**. Provider capability selection, detailed event schema, payload retention and actual readback proof remain open before integration.

## 8. Phased implementation boundary (future, not in this issue's design phase)

1. Pure proof schema + verifier and deterministic fixtures. No provider network, no Work writes.
2. Host-side read-only capability for **one** provider with authenticated stable receipt and complete-response semantics. No `CognitionPort.complete` changes.
3. Explicit proof/admission surface that reuses Gen2's exact CAS-bound outcome path, emits audit provenance, and is idempotent across restart.
4. Crash/replay and cross-provider contract conformance; only then consider additional providers or policy-approved automation.

**Exit condition for this design phase:** reviewed invariant set, proof-level policy, test matrix, and decision on receipt/audit storage. No claims of generalized exactly-once execution or automatic reconciliation based solely on the DW3 pilot.
